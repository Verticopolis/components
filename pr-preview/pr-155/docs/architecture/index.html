Architecture

How the components are put together: the render model a game fills, the Excalibur scene that draws it, how a frame and a press flow, the procedural sprites and the atlas, the Win95 windows and their stylesheet, the audio layer, and how the package is built and released.

The diagrams are Mermaid; GitHub renders them inline. The README lists every subpath and its semver promise, and the deeper pages are in docs/: the sprite atlas, the design system, the desk and the audio layer.

The package at a glance

Section titled “The package at a glance”

The components know nothing about the simulation. A game owns its world and its rules, fills the render model from them, and hands the scene its input hooks. Everything here reads that model, draws it, plays it and frames it in Win95 chrome.

flowchart TD
    subgraph game["A game (the web game or any other)"]
        World["its own world and rules"]
        Fill["fills the render model"]
        Ctl["controllers and UI"]
    end

    subgraph pkg["@verticopolis/components"]
        Model["render/renderModel · render/towerSource<br/>(stable)"]
        Scene["render/excalibur/<br/>TowerEngine, the scene"]
        Render["render/<br/>geometry, sprites, overview map, atlas"]
        Pres["presentation/<br/>what each kind of room shows"]
        Windows["windows/* (src/ui/)<br/>menu bar, windows, message boxes, the desk,<br/>title screen, bars, Tools, Map, dialogs<br/>(stable)"]
        Styles["styles.css · styles/*<br/>(stable)"]
        Astro["astro/<br/>docs title bar and title screen"]
        Audio["audio/<br/>Tone.js music and ambience"]

    Model --> Scene

Excalibur, Tone.js and lit-html are peer dependencies. Only the sprite atlas bake uses the one direct dependency, fflate. The Astro components are the one piece a game does not run: a docs site (the player’s manual, the engine docs, the component gallery) compiles them when it is built.

The render model: the only way in

Section titled “The render model: the only way in”

render/renderModel declares everything the renderer reads, as plain interfaces:

  • RenderSim: one frame of the world (the clock, the tower, the crowd, the effects, the view).
  • RenderCatalog: the catalog fields the renderer draws from (sizes, kinds, subtypes), with FacilityKind the kinds this build has art for.
  • RenderRules: whether a room is present and operating, and the zoom limits.

A game whose objects already have those fields passes them through with no copy, and its own typecheck fails when one of them drops or retypes a field the renderer reads. Each tower gets its catalog and rules once, through useTowerSource(tower, { catalog, rules }) in render/towerSource.

flowchart LR
    Game["a game's frame<br/>(its own types)"] -->|"pass through, no copy"| RS["RenderSim"]
    GameCat["a game's catalog"] -->|"useTowerSource"| RC["RenderCatalog"]
    GameRules["a game's rule answers"] -->|"useTowerSource"| RR["RenderRules"]
    RC --> Check["presentation/catalogCheck<br/>refuseForeignCatalogs"]
    RS --> Scene["TowerEngine"]
    RC --> Scene
    RR --> Scene
    Check -.refuses a kind with no art.-> Game

The unit tests, the gallery and the atlas bake fill the model from hand-written fixtures (src/tests/catalogFixture.ts, one per mode, and src/tests/renderRules.ts), so nothing here needs a running world.

One frame

Section titled “One frame”

Excalibur drives the loop. Each frame TowerEngine (src/render/excalibur/TowerEngine.ts) first runs its own per-frame work (towerFrame.ts: the decorative clock, the event visuals, the lighting and the sky), then calls the game’s onUpdate(ms), where the game steps its world and refreshes the render model, then brings the scene in line with the model. Drawing never writes back to the model. A frame that throws is handed to onFrameError, so one bad frame skips instead of stopping Excalibur’s loop.

sequenceDiagram
    participant EX as Excalibur loop
    participant TE as TowerEngine
    participant G as the game
    participant SC as scene modules
    participant A as audio

    EX->>TE: tick(ms) every frame
    TE->>SC: towerFrame: decorative clock, event visuals, lighting, sky
    TE->>G: onUpdate(ms)
    Note over G: steps its world,<br/>refreshes the render model
    TE->>SC: towerSyncSchedule / towerReconcile: rebuild what changed
    TE->>SC: budgeted region repaints, motion, crowd
    SC-->>EX: draw (reads RenderSim only)
    G->>TE: focus()
    TE-->>G: ViewFocus (camera floor, zoom, hour, weather, crowd)
    G->>A: update(focus) about 6 Hz

The scene splits by layer, one module each: the structure and its tiles (towerStructTiles.ts, towerReconcile.ts), the crowd (towerCrowd*.ts, crowdCull.ts), the elevator cabs (cab*.ts), the scenery and sky (towerScenery*.ts, sceneBake.ts), the event effects (fire response, the thief, the metro) and the overlay that draws the placement ghost and its label (towerOverlay.ts, towerGhostLabel.ts).

Input: a press becomes a hook

Section titled “Input: a press becomes a hook”

The scene owns the camera and pointer input (towerInputCamera.ts). It classifies the gesture (tap, drag, long press, pinch, a secondary press) and calls the game back through a hook with the tile, the floor and a pick() that hit-tests the world (towerPick.ts) the first time the hook asks, so a hover or a drag that never needs the entity under the pointer scans nothing. The game decides what the press means.

flowchart LR
    Pointer["pointer · touch · keyboard"] --> TE["TowerEngine<br/>Excalibur input"]
    TE --> Cam["towerInputCamera<br/>pan, zoom"]
    TE --> Press["pressLifecycle · longPress<br/>pinchTracker · pointerButtonGuard"]
    Press --> Hooks["onTap · onActionDown/Move/Up<br/>onHover · onLongPress · onSecondary<br/>onExtendTo"]
    Cam --> Hooks
    Hooks -->|"pick(), when asked"| Pick["towerPick<br/>hit test"]
    Hooks --> Game["the game's controllers"]
    Game -->|"ghost, selection"| Overlay["towerOverlay"]

Sprites and the atlas

Section titled “Sprites and the atlas”

Every sprite is procedural: render/pixelSprites/ and render/sprites/ paint rooms, people, cars and scenery in code, and the scene draws them directly. The atlas bake (render/atlas/) paints the same sprites into one sheet with a manifest, for a frontend that would rather load images; each release carries the baked atlas. docs/atlas.md covers the archive, the manifest, depth layers and how it is checked.

flowchart LR
    Cat["a render catalog<br/>(fixture or a game's own)"] --> Paint["pixelSprites/ · sprites/<br/>procedural painters"]
    Paint --> Scene["the scene<br/>draws at run time"]
    Paint --> Bake["render/atlas/<br/>compose · pack · png"]
    Bake --> Archive["atlas archive<br/>sheet + manifest"]
    Archive --> Verify["atlas/verify<br/>checks every frame"]
    Archive --> Release["attached to each release"]

Windows and styles

Section titled “Windows and styles”

The Win95 chrome is DOM: the menu bar (src/ui/menuBar.ts), modal message boxes (ModalShell in uiModal.ts), movable windows (movableWindow.ts), the 1994 desk (src/ui/desk/: its window manager, windows, taskbar and Start menu, the Control Panel, the Help window that frames the player’s manual, the title screen on the desk, and deskPocket.ts for phones and tablets), the title screen (src/ui/titleScreen/), the Information bar and status bar (src/ui/bars/), the Tools window (src/ui/palette/), the Map window (overviewMapWindow.ts), the inspect card (inspectCard.ts, inspectPanel.ts), the editor card (editorCard.ts, and shaftEditor.ts for a shaft), the Open and Save As windows (src/ui/fileDialog/), the scenario lists and the New Scenario dialog (scenarioList.ts, newScenario.ts), the screen savers (src/ui/screenSaver/), the Appearance dialog, the alert card and update box, the fireworks, the page not found desk, a docs site’s menu bar (siteMenu.ts) and the icons. Each window module imports the stylesheet it needs. docs/desk.md has the desk’s pieces and rules.

A docs site’s title bar and front page are Astro components in src/astro/ (TitleBar.astro, TitleScreen.astro), compiled by the site when it is built. They put no DOM on the page at run time, so they are the one part of the package not drawn with lit-html. styles.css is the whole look in one import; every sheet sits in a cascade layer under vc, so a page’s own unlayered rule always wins and the pieces keep their order. The sheets a window module imports itself sit in vc.windows, below the game’s layout, so a second copy a bundler puts after styles.css cannot undo what the page layer changes in them; the README’s Cascade layers section has the full order. docs/design-system.md is the contract for the tokens, the components and the window grammar.

The DOM is drawn with lit-html templates, and an element’s events are bound in its template (@click, @keydown). A page hands a component a model and writes no markup of its own. The menu bar draws itself from a MenuBarModel (menuBarTemplate.ts); a page re-renders it with a changed model (fresh check marks as a menu opens), and lit touches only what changed. Listeners stay imperative only where no template owns the element: the window and the document (the menu bar’s outside press and Alt keys), and a window the game draws that a module moves (movableWindow.ts).

Audio

Section titled “Audio”

The audio layer synthesizes the game’s music and ambience live on Tone.js. A small facade loads at boot; the heavy audio engine loads on the first gesture. The game fires cues and hands over the camera’s focus; the layer never decides a rule. docs/audio.md has the module map, the bus graph, the lifecycle and the ambient layer.
